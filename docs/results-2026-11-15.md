# Initial feasibility result — 2026-11-15

**Java 25 works as a standalone WASI command with this toolchain. Published GuicedEE Guice does not compile to that target.**

## Observed gates

| Gate | Observed local result |
| --- | --- |
| JVM baseline | PASS: all 3 tests, 0 failures/errors/skips |
| Java 25 → TeaVM WASI → Wasmtime | PASS: expected output, exit 0 |
| Guice constructor-only → WASI | FAIL: compiler exit 1; no runtime execution |
| Guice constructor/provider/singleton/scope/interceptor → WASI | FAIL: compiler exit 1; no runtime execution |
| WASI HTTP component | NOT TESTED |
| Full GuicedEE/Vert.x bootstrap and request lifecycle | NOT TESTED |

The Java sources compiled to class-file major version **69** (Java 25). This was not achieved by lowering the Java target.
The successful module is **329,422 bytes** and executes without Node.js or a browser:

```text
WASI_BASELINE_OK sum=42 exception=caught
```

This verifies allocation, collection/stream computation, exception handling and WASI stdout. It does not establish a WASI HTTP export.
Observed process duration is not a throughput/cold-start benchmark.

## Actual compiler blockers

Both Guice probes produced **38 unique missing-class/method diagnostics**. These include:

```text
Class java.lang.reflect.ParameterizedType was not found
Class java.lang.reflect.GenericArrayType was not found
Class java.lang.reflect.WildcardType was not found
Class java.lang.reflect.TypeVariable was not found
Class java.util.concurrent.locks.ReentrantLock was not found
Class java.util.concurrent.atomic.AtomicReferenceArray was not found
Class java.lang.reflect.Executable was not found
Class java.util.concurrent.locks.LockSupport was not found
Class sun.misc.Unsafe was not found
Class java.lang.reflect.Proxy was not found
```

Further missing methods concern generic/annotated reflection, parameter metadata, Guava cache locks and concurrent collections.
The constructor-only probe registers no application interceptors or custom scopes. Its failure shows that the blocker is broader
than this experiment's interception test. It does not prove that every possible Guice/TeaVM adaptation must fail.

The JVM tests establish that the source and published dependency can perform the requested Guice operations on Java 25.
The WASI compiler failures therefore represent compatibility findings, not a successful service deployment.

## Consequence and next experiment

A compiler flag or HTTP wrapper will not supply these missing Java APIs. The next useful investigation is whether a bounded
Guice compatibility layer can preserve generic reflection, provider/scoping semantics and interception on a maintained WASI compiler.
Replacing locks or reflection with no-op stubs would not be acceptable evidence.

Once that gate passes, add a real WASI HTTP/component export, then address GuicedEE's Vert.x-backed contexts, startup and transport.
Do not invest in full persistence/messaging integration before those gates pass.

## Evidence

The [local snapshots](evidence/) contain gate results, the successful runtime output and the complete distinct missing-API lists.
The GitHub Actions matrix independently repeats these gates on Linux/JDK 25 and uploads full compiler logs, test reports and produced
Wasm files. Compatibility failures intentionally fail their jobs; there is no `continue-on-error` or synthetic success.

The GuicedEE Creator validator passes Maven/Java/BOM/test/JPMS/package checks, but reports the absent full-framework bootstrap.
That is a documented scope exception: these substrate probes intentionally do not invoke `GuiceApplication` or start Vert.x.
